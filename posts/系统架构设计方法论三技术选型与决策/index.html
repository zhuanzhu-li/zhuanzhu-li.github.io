系统架构设计方法论（三）：技术选型与决策

前言

技术选型是最容易被低估的架构决策。很多系统不是被业务难死的，而是被选型拖死的：选了个"很潮"但不成熟的技术，踩坑三个月；或者"大家都在用"所以跟着选，业务形态根本对不上。

选型的本质是用可验证的证据做决策，而不是凭感觉。本文给出一套可复用的选型方法论：前置条件、评估维度、决策框架和落地案例。

一、选型前置：回到需求

选型前先回答三个问题，答案不在技术而在业务：

  1. 问题是什么——要解决的是存储、通信、计算还是检索问题
  2. 约束是什么——团队熟悉度、成本、合规、运维能力
  3. 规模与演进预期——3 年后数据量、QPS、团队规模

这三个问题（对应系列第一篇的需求与边界）没想清楚，对比矩阵就是空中楼阁。

二、评估维度

候选技术放到统一的维度下评估：

维度 关注点 反面教材
成熟度 版本历史、大规模落地案例 选 0.x 版本上生产
社区与生态 文档、Issue 响应、周边工具 出问题没人问
性能 基准测试是否满足指标 压测都没做就定
运维成本 部署、监控、排障的复杂度 上线后没人会运维
团队熟悉度 学习曲线、招聘难度 全组没人写过
演进性 版本升级、API 稳定性 升级一次伤筋动骨
许可证与合规 开源协议、数据合规 用了禁止商用协议

评估不是简单求和，而是先设否决项，再谈加权：任何一项踩到硬约束（比如许可证不允许商用），一票否决。

三、决策框架：从对比矩阵到 POC

3.1 对比矩阵

矩阵列出候选方案 × 评估维度，每格给证据（文档链接、压测数据、社区讨论），而不是拍脑袋打分。

维度 候选 A（Kafka） 候选 B（RabbitMQ）
吞吐 百万级/s（官方基准） 万级/s
消息模型 分区日志 队列/路由
延迟 毫秒级（批量优化前） 微秒~毫秒级
运维 需要管理分区、副本 轻量，管理简单
生态 大数据生态标配 Spring 生态友好

3.2 POC 验证

对关键指标做最小成本的概念验证，验证点要提前写死：

POC 验证单（例：消息中间件）：
1. 峰值 5000 QPS 下单链路，端到端延迟 TP99 < 500ms
2. 消费者宕机 10 分钟，消息不丢、恢复后积压追平
3. 集群 3 节点挂 1 节点，服务不中断
4. 团队 2 人一周内能完成核心功能

POC 通过率比任何专家意见都可信。

3.3 决策记录

选定后写 ADR（架构决策记录），把背景、候选、评估、决定、后果记下来。这个习惯会在系列第五篇（演进与治理）里继续展开。

四、自研 vs 开源 vs 商业

选项 适用场景 风险
开源 需求通用、社区活跃 版本升级、维护责任
商业 核心业务、要支持与 SLA 成本、锁定
自研 开源满足不了、构成核心竞争力 长期维护成本最高

自研要极其克制：一个内部组件一旦开源能满足，就失去自研理由。反过来，如果这个组件是业务护城河（比如支付的风控规则引擎），自研反而合理。

五、权衡取舍

  • 新 vs 稳：新技术带来的红利 vs 踩坑成本。生产环境遵循"稳定 > 性能 > 功能"
  • 性能 vs 运维复杂度：极致性能往往意味着更复杂的运维（如自建 ES 集群 vs 托管版）
  • 绑定 vs 解耦：选型要评估迁移成本，但也不必为"万一换"过度抽象，抽象本身也是成本

六、落地案例

博客系列里已经有大量选型案例可以对照：

  • 注册中心/配置中心：Nacos 综合实战说明了为什么选 Nacos 而非 Eureka——配置中心一体化、AP 模型适合服务发现
  • 消息队列：Kafka vs RabbitMQ 的选择要看吞吐与模型：Kafka 核心架构 vs RabbitMQ 核心架构
  • 搜索引擎：ES 核心架构展示了倒排索引的适用边界——全文检索、聚合分析，而不是所有查询
  • 工作流引擎：工作流选型与 Flowable 核心概念是一篇典型的"需求 → 候选 → 决策"选型文
  • 技术栈组合：WebGIS 概述与技术栈选型从空间数据业务出发推导整套技术栈

每个案例的共通点：先定义问题和约束，再评估，再验证，最后记录决策。

七、面试考察点与自查清单

高频面试题：

  1. “为什么选 Redis 而不是 Memcached？"——从数据结构、持久化、集群、业务需求角度答，而不是背结论
  2. “怎么组织选型报告？"——问题 → 候选 → 维度 → 证据 → 决定
  3. “开源自研怎么选？"——通用问题用开源，核心壁垒才自研
  4. “技术选型最大的坑？"——跳过 POC、被情绪带节奏、忽略运维成本

自查清单：

  • 每次选型有对比矩阵和证据
  • 关键指标做过 POC 验证
  • 选型结果有 ADR 记录
  • 能说清"不选另一个方案"的原因
