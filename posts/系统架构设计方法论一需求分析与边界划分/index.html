系统架构设计方法论（一）：需求分析与边界划分

前言

架构师最常犯的错误，不是方案设计得不够精妙，而是把方案做在了错误的问题上。需求还没厘清就开始选型、画架构图，等系统上线才发现：QPS 估错了、边界划错了、非功能需求根本没定义过。返工的成本，往往是初版设计成本的十倍。

本文是"系统架构设计方法论"系列的第一篇，聚焦架构设计的起点——需求分析与边界划分。只有把"做什么、做到什么程度、边界在哪里"想清楚，后续的模块化、选型、质量属性设计才有依据。

一、从业务目标推导架构属性

架构设计的本质是在约束下做权衡，而权衡的依据来自业务目标。需求分析的第一步，是把业务目标翻译成可量化的架构属性。

业务目标 架构属性 典型量化指标
支撑大促峰值 性能/扩展性 峰值 QPS、TP99 延迟
交易不能出错 一致性/可靠性 数据不一致率、资金差错率
停机即损失 可用性 SLA 99.9%、RTO/RPO
快速试错上线 可维护性/演进性 发版频率、需求交付周期
控制成本 成本效益 单请求成本、资源利用率

关键动作是显式化：把"系统要稳定"这种口号，变成"可用性 99.9%，全年停机不超过 8.8 小时；核心链路 TP99 < 200ms"这样的指标。指标一旦显式，架构取舍就有了解题方向。

二、需求分析方法论

2.1 功能需求与非功能需求

功能需求决定系统"做什么"，非功能需求（NFR）决定系统"做到什么程度"。后者才是架构设计的真正输入。

NFR 显式化的例子：

模糊描述 显式化后
系统要快 核心接口 TP99 < 200ms，P95 < 100ms
系统要稳 可用性 ≥ 99.9%，RTO < 30min，RPO < 5min
数据不能丢 消息投递可靠性 ≥ 99.99%，落库后不丢
要能撑住活动 预估峰值 5000 QPS，支持 2 倍余量弹性

注意 NFR 之间会互相打架（一致性 vs 可用性、延迟 vs 吞吐），显式化的意义在于让冲突暴露在设计之前，而不是上线之后。

2.2 场景与流量模型

有经验的架构师会先画流量模型再画架构图：

每日 UV 100万，人均 20 次请求 → 日请求 2000万
业务集中在 2 小时晚高峰 → 峰值 = 2000万 / 7200s × 集中系数 2 ≈ 5555 QPS
读写比 10:1 → 读 5000 QPS，写 500 QPS
单条数据 1KB → 日新增 500G，一年 180T

从流量模型能直接推导出：需不需要缓存、需不需要分库分表、需不需要消息队列削峰、用多少实例。这套估算在面试"设计一个高并发系统"时也是标准开场。

2.3 约束识别

架构设计不是白纸作画，约束必须前置：

  • 成本约束：服务器预算、云资源上限
  • 团队约束：团队规模、技术栈熟悉度、排期
  • 时间约束：上线时间窗口、里程碑
  • 合规约束：数据安全、审计、监管要求（支付系统尤甚）

约束不识别，方案再好也落不了地。

三、边界划分

3.1 从问题域到限界上下文

边界划分的第一层是业务域。用领域驱动设计（DDD）的话说，就是把问题域切成若干限界上下文（Bounded Context），每个上下文有自己的模型语言，上下文之间通过明确接口协作。

┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  客户域      │    │  交易域      │    │  履约域      │
│  Customer   │───▶│  Order      │───▶│  Fulfillment│
└─────────────┘    └─────────────┘    └─────────────┘
       │                  │                   │
       ▼                  ▼                   ▼
┌─────────────────────────────────────────────────┐
│              共享内核 / 公共能力                    │
└─────────────────────────────────────────────────┘

边界划分的信号不是"好不好看"，而是变化频率、团队结构、故障隔离、扩展维度：

划分信号 说明 例子
变化频率 变化节奏不同的部分分开 商品模型稳定，营销规则频繁变
团队结构 康威定律：系统结构跟随沟通结构 支付组、渠道组、对账组
故障隔离 一个挂不能带崩另一个 风控服务不能拖垮支付主链路
扩展维度 扩容单位不同则分开 读多写少的部分独立扩缓存

3.2 系统边界 / 模块边界 / 服务边界

三个边界是不同粒度的同一问题：

  • 系统边界：对外提供什么能力，输入输出契约是什么
  • 模块边界：代码层如何组织，依赖方向如何约束
  • 服务边界：运行时如何部署、如何隔离故障

很多团队的问题在于跳级：还没理清模块边界就先拆服务，结果服务之间循环调用，比单体更乱。

3.3 边界划分的实践准则

  1. 先按业务能力切，不按技术切（“订单服务"而不是"数据库服务”）
  2. 边界两侧用契约通信，不共享内部表结构
  3. 跨边界的操作要么事务化，要么事件化，不搞隐式耦合
  4. 不确定的边界先合并，等变化信号出现再拆

四、权衡取舍

边界划分的核心权衡是粗与细：

  • 边界过粗 → 模块互相渗透，改一处崩一片，团队互相踩脚
  • 边界过细 → 分布式复杂度爆炸：事务、一致性、链路追踪、部署成本全上来

更聪明的做法是演进式划分：单体起步、模块内聚，当"变化频率差异 + 团队规模 + 故障影响"三个信号同时出现时再拆。拆服务是手段不是目的。

另一个权衡是需求确定性：需求模糊时先做薄边界、快速验证，而不是一步到位画完整套领域模型。

五、落地案例：支付系统的域划分

支付系统是边界划分的教科书案例。回顾支付系统架构设计（一）：整体架构概览，支付系统按业务域分为支付、退款、签约/代扣、查询，再按能力分为账务、渠道、风控、对账。

其中最关键的设计决策是支付与账务分离：支付订单关心"这笔支付成没成"，资金账户关心"钱记对没记对"，两者变化频率和故障影响完全不同，必须拆开。更底层的建模见支付核心领域建模（DDD），那里对限界上下文和聚合根有完整展开。

另一个案例是 WebGIS 项目：空间数据的读写、地图服务、业务查询属于不同的变化维度，WebGIS 概述与技术栈选型就是从业务边界出发推导技术栈的过程。

六、面试考察点与自查清单

高频面试题：

  1. “给你一个系统，你怎么做容量估算？"——流量模型 → 峰值 QPS → 资源推导
  2. “这个服务该不该拆？"——变化频率、团队、故障隔离、扩展维度四信号
  3. “非功能需求怎么落地到设计？"——NFR 显式化 → 架构属性 → 方案取舍
  4. “限界上下文是什么？怎么划？"——统一语言、模型边界、上下文映射

自查清单：

  • 能说出系统核心指标：QPS、TP99、SLA、数据规模
  • 能画出流量模型并推导资源量级
  • 能说明每个边界的划分依据（变化/团队/故障/扩展）
  • 能说清系统/模块/服务三个边界各自在哪
