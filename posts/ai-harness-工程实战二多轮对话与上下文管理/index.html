前言

上一篇，我们把"一次模型调用"封装成了可靠的 LLMClient。但真实产品里，用户不会只问一句：客服助手要来回追问，编程助手要连续修改，业务 Agent 要和用户确认细节。这一篇解决的就是"让模型记住对话"以及随之而来的上下文管理问题。

你会发现，多轮对话远不是"把消息都存下来"那么简单——存下来只是第一步，怎么在有限的窗口和预算里装下越来越长的历史，才是真正的工程问题。

一、场景：让模型"记住"对话

模型本身是无状态的：每一次请求，你都得把完整的对话历史塞进 messages 里，它才知道"前因后果"。所以多轮对话的本质是由 harness 来维护状态。

最简单的实现，就是用一个全局列表：

messages = []

def chat(user_text: str) -> str:
    messages.append({"role": "user", "content": user_text})
    reply = client.chat(messages)
    messages.append({"role": "assistant", "content": reply})
    return reply

看起来没毛病，跑两周就会出事。

二、它暴露了哪些问题

  • 会话互相污染：全局列表意味着所有用户共享同一份记忆。A 用户刚问完"我的订单号是多少"，B 用户的下一个问题里就带着 A 的历史——这在线上是事故级别的 bug。
  • 上下文无限增长：每轮都全量重发。聊到第 50 轮时，一次请求可能要带几万 token，超过模型窗口上限直接报错，没超的也在烧钱。
  • 角色与顺序全靠手拼：system prompt、历史、最新消息拼接逻辑散落在各处，改一处忘一处。
  • 无法定位与清理：想清空某个会话、想回滚到某个节点，全局列表根本做不到。

这些问题的根源是同一个：会话状态没有一个明确的所有者。

三、工程化演进：会话对象 + 上下文预算

1. 会话隔离：Session

第一步，把"对话状态"收进一个对象里，一个用户一个 Session：

@dataclass
class Session:
    system_prompt: str = ""
    messages: list[dict[str, str]] = field(default_factory=list)

    def user(self, content: str) -> None:
        self.messages.append({"role": "user", "content": content})

    def assistant(self, content: str) -> None:
        self.messages.append({"role": "assistant", "content": content})

    def to_messages(self) -> list[dict[str, str]]:
        if not self.system_prompt:
            return list(self.messages)
        return [{"role": "system", "content": self.system_prompt}, *self.messages]

会话互不污染，并发场景下每个用户各管各的。system_prompt 的拼装也收口到了 to_messages()。

2. 先估算，再裁剪

第二步是控制上下文规模。要裁剪，先得知道"现在有多少 token"。生产环境常用 tiktoken 精确计数，但为了保持零框架依赖，教程先用启发式估算（中文约 1 字 ≈ 0.5~1 token，按字符数折算），足够我们在工程层面把逻辑讲清楚：

CHARS_PER_TOKEN = 2.0

def estimate_tokens(text: str) -> int:
    if not text:
        return 0
    return max(1, int(len(text) / CHARS_PER_TOKEN))

3. 窗口截断：预算内保留最近的

ContextPolicy 定义上下文预算（max_tokens - reserve_tokens，后者留给模型回复）。超预算时，trim_context 优先保留 system prompt 和最近的对话，从最旧的消息开始丢：

def _window(system, body, policy):
    total = estimate_messages_tokens(system)
    kept = []
    for message in reversed(body):          # 从最新往最旧遍历
        cost = estimate_messages_tokens([message])
        if total + cost > policy.context_budget:
            break
        kept.append(message)
        total += cost
    return system + list(reversed(kept))

为什么优先保最近的？因为模型对最近几轮上下文最敏感——“刚刚说的需求"比"三小时前聊的内容"重要得多。

4. 摘要压缩：比直接丢更友好

窗口截断的代价是"硬丢”，重要信息可能随之丢失。所以再给一个 summary 模式：把最早的一批消息交给一个摘要回调（回调里可以再调一次模型），压缩成一段摘要，再继续按窗口截断兜底：

policy = ContextPolicy(
    max_tokens=2000,
    reserve_tokens=200,
    mode="summary",
    summarizer=lambda oldest: f"（此前对话摘要）{summarize_with_llm(oldest)}",
)
messages = trim_context(session, policy)

演示脚本里的效果：

裁剪前：11 条消息，约 1200 token
裁剪后：5 条消息，约 380 token
预算上限：1800 token

四、为什么这样设计

  • 状态要有明确的所有者：Session 把"记忆"从全局变成实例，隔离问题迎刃而解，也为后面做并发、持久化留了位置。
  • 估算先行、裁剪兜底：不估算就裁剪是盲人摸象；估算用零依赖启发式，是"能跑"和"精确"之间的合理起点。
  • 摘要走回调：harness 不绑定任何摘要模型，只定义"把一段历史变成一段摘要"的接口，具体实现由上层决定——这保持了 harness 的薄和可替换。
  • 为后续演进留口：Session 之后会成为 Agent 的一部分；工具调用循环里，模型每执行一步工具，也都是往 Session 里追加消息。

五、小结

本篇的收获：

  1. 多轮对话的本质是 harness 维护状态，状态必须有明确的所有者（Session）。
  2. 上下文不是"全塞进去"，而是"预算内最优化"：估算 → 裁剪 → 必要时压缩。
  3. 截断优先保 system 和最近消息；摘要压缩是"先压缩、再兜底"的升级策略。
