系统架构设计方法论（四）：性能、可用性与扩展性

前言

性能、可用性、扩展性，是系统架构面试里出现频率最高的三个词，也是线上事故最集中的三个来源。三者看似独立，实际是同一个问题的三个侧面：当压力、故障、增长到来时，系统如何应对。

这篇文章给出一套方法论框架，不深入某个具体机制（那些在分布式、支付、Spring Cloud 系列里都有），而是讲清楚"遇到这类问题，思考路径是什么"。

一、性能方法论

1.1 先定义性能目标

没有目标的性能优化都是玄学。目标包括：吞吐（QPS/TPS）、延迟（TP99/TP95）、资源占用（CPU/内存），且要放在具体场景里（读多还是写多、热数据比例）。

1.2 容量规划

容量规划流程：
1. 流量模型估算（系列第一篇的方法）
2. 单机基准：压测出单实例能扛多少 QPS
3. 实例数 = 峰值 QPS / 单机 QPS × 冗余系数（通常 2）
4. 加上增长预期，留出演进空间

压测数据是唯一可信的输入，基准没跑出来之前，所有"应该够"都是猜测。

1.3 性能设计手段

按性价比排序的常用手段：

  1. 缓存：读多写少场景的第一选择。Redis 缓存设计与实战讲了缓存穿透、击穿、雪崩的完整解法
  2. 索引：查询慢先看执行计划。MySQL 索引原理与优化是最常用的性能武器
  3. 异步化：非核心链路异步化，削峰填谷
  4. 读写分离：读压力大时主从分离

1.4 定位问题

性能问题定位靠数据不靠猜：全链路追踪（Sleuth + Zipkin、支付可观测性)把慢请求的每一跳打开，先找到瓶颈在哪一层，再动手。

二、可用性方法论

2.1 定义可用性

可用性 = 服务正常时间 / 总时间。99.9% 意味着全年最多 8.8 小时不可用，99.99% 是 52.6 分钟。SLA 一旦定义，故障处理和容量规划都有标准。

2.2 设计手段

可用性三板斧：
1. 冗余 + 无状态：多副本部署，任意节点可替换
   （见分布式设计思想：无状态设计）
2. 故障隔离 + 降级：把故障圈在局部，非核心功能让路
   （降级熔断限流：Sentinel）
3. 容灾 + 演练：预案不是写了就有用，要定期演练
   （支付高可用与容灾）

降级、熔断、限流是三个不同动作，面试高频考点：

动作 触发 目的 例子
限流 流量超阈值 保护自己 每秒放 1000 个请求
熔断 下游故障率高 保护下游 失败率 > 50% 直接拒绝
降级 资源不足/依赖失败 保住核心 推荐位返回空列表

具体实现见Sentinel 流量治理和分布式系统高可用与流量治理。

2.3 故障模型

设计时先假设一切都会失败：网络会断、机器会宕、消息会丢、调用会超时。围绕这些假设做冗余、重试、幂等、兜底——这正是分布式系统设计思想与方法论的核心。

三、扩展性方法论

3.1 水平扩展的前提：无状态

无状态是扩展性的地基：节点不保存用户状态，请求打到任意节点结果一样，才能随便加机器。状态交给共享存储（DB/Redis）。

3.2 数据扩展

数据量增长后，单库单表扛不住：

  • 读写分离：读压力与写压力分开
  • 分库分表：按维度（用户 ID、订单 ID）分片
  • 缓存：热点数据前置

分片带来分布式问题（跨片事务、聚合查询），所以分片是最后手段，先用缓存和索引。

3.3 服务扩展

服务层面两种扩展方向：

垂直扩展：加 CPU/内存 —— 有物理上限
水平扩展：加实例 —— 配合负载均衡，无上限（有状态是障碍）

服务拆分后，消息队列承担削峰填谷：
上游 → MQ → 下游按消费能力处理
（见 Kafka/RabbitMQ 系列）

云原生时代，扩展性交给平台：K8s 架构与核心概念的 HPA 让实例数跟随负载自动伸缩。

四、三者的权衡

三个质量属性经常互相打架：

  • 性能 vs 一致性：CAP 里的一致性-可用性权衡，分布式理论 CAP/BASE/一致性有完整论述
  • 可用性 vs 一致性：强一致（同步复制）会牺牲可用性和延迟，最终一致（异步）换可用性
  • 扩展性 vs 复杂度：拆得越细扩展越灵活，但事务、追踪、运维复杂度指数上升

成本三角是终极约束：性能、成本、复杂度，最多同时优化两个。架构师的职责不是"全部都要"，而是根据业务目标（系列第一篇）明确优先序。

五、落地案例：秒杀系统设计串联

把三个方法论串起来的标准面试题——设计一个秒杀系统：

1. 性能：提前把库存预热到 Redis，读请求走缓存
2. 限流：网关按用户/IP/QPS 限流，挡掉大部分无效请求
3. 削峰：下单请求进 MQ，异步消费落库
4. 幂等：同一用户重复提交只生效一次（唯一键/状态机）
5. 降级：非核心功能（排行榜、推荐）让路
6. 扩展：无状态服务水平扩容，Redis/DB 按读压力分片

每一步都有对应的方法论依据，这就是"高并发系统设计"的标准答题框架。支付场景的完整落地可看支付高可用与容灾。

六、面试考察点与自查清单

高频面试题：

  1. “设计一个高并发秒杀系统”——缓存、限流、削峰、幂等、降级、扩展六板斧
  2. “缓存一致性怎么保证？"——Cache Aside、删除缓存、最终一致（Redis 缓存设计)
  3. “熔断和降级的区别？"——熔断保护下游、降级保护核心业务，触发条件和目标都不同
  4. “什么时候该分库分表？"——容量/写入/查询瓶颈，且缓存、索引、读写分离都到极限

自查清单：

  • 能说清系统当前容量：峰值 QPS、单机能力、冗余系数
  • 每个核心链路都有故障预案
  • 能画出系统的扩展路径（无状态化 → 分片 → 拆分）
  • 能说出三个质量属性在本系统的优先级和理由
