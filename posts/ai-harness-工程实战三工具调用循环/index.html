前言

前两篇，模型能"说话"了，也能"记住"上下文了。但用户要的不是聊天机器人，而是能干活的 Agent：查天气、算数据、读写文件、调接口。这一篇是这个系列的分水岭——我们让模型自己决定"调用什么工具、拿到结果、继续思考"，一个最小的 Agent 就此诞生。

核心就一个词：循环。

一、场景：让模型"干活"

假设你的业务要做一个天气助手。用户问"北京天气怎么样？"，模型不会查天气——它只会生成文本。所以要让模型"使用工具"：模型输出"我要调用 get_weather，参数是北京"，harness 去执行这个函数，把结果喂回给模型，模型再组织成回答。

这一步的工程难点不是函数本身，而是模型和代码之间的协议：模型怎么表达意图？结果怎么回传？循环什么时候停？

二、朴素实现：让模型输出 JSON，自己解析

最直觉的做法：在 prompt 里让模型输出一个 JSON 指定"函数名 + 参数"，然后手动解析执行：

def naive_agent(question: str) -> str:
    prompt = f"""你是天气助手。需要查天气时，输出 JSON：
{{"tool": "get_weather", "arguments": {{"city": "北京"}}}}
问题：{question}"""
    reply = client.chat([{"role": "user", "content": prompt}])
    call = json.loads(reply)                       # 祈祷它是合法 JSON
    result = globals()[call["tool"]](**call["arguments"])
    return result

本地演示能跑通，但它是"赌运气"的代码。

三、它暴露了哪些问题

  • 模型输出不稳定：模型可能给你 ```json 围栏、前后夹带解释文字、甚至 JSON 损坏——json.loads 直接崩。
  • 工具定义与实现重复：工具的"使用说明"写在 prompt 字符串里，实现写死在代码里，改参数要同步改两处。
  • 结果回填没有约定：工具结果怎么回到模型手里？直接拼进下一轮 prompt？谁来拼？顺序怎么保证？
  • 没有终止条件：模型可能反复要求调用工具，循环停不下来，钱烧完为止。
  • 工具名写错就崩：globals()[call["tool"]] 找不到键直接 KeyError。

这些问题的本质是：模型和工具之间缺一层正式的协议和一个负责执行的主循环。

四、工程化演进：工具注册表 + Agent 主循环

1. 工具注册表：把"函数"升级成"工具"

用装饰器给函数加上名字、描述、参数 Schema（JSON Schema，OpenAI 风格）和权限声明：

@tool(
    name="get_weather",
    description="查询指定城市的天气",
    parameters={
        "type": "object",
        "properties": {"city": {"type": "string", "description": "城市名，如：北京"}},
        "required": ["city"],
    },
)
def get_weather(city: str) -> str:
    return f"{city}：晴，28°C"

ToolRegistry 负责注册和按名字查找，schema 由装饰器统一生成，描述和实现不再各写各的：

registry = ToolRegistry()
registry.register(get_weather)
schemas = registry.schemas()   # 直接作为 tools 参数发给模型

2. Agent 主循环：感知 → 思考 → 行动

Agent 把会话、模型、工具串成一个循环：

for step in range(1, self.max_steps + 1):
    messages = trim_context(self.session, self.context_policy)
    data = self.client.chat_completion(messages, tools=self.registry.schemas())
    message = data["choices"][0]["message"]
    tool_calls = message.get("tool_calls") or []

    if not tool_calls:
        content = message.get("content") or ""
        self.session.assistant(content)
        return content

    self.session.messages.append({          # 记录模型的调用意图
        "role": "assistant", "content": message.get("content"),
        "tool_calls": tool_calls,
    })
    for call in tool_calls:
        tool_impl = self.registry.get(call["function"]["name"])
        if tool_impl is None:
            result = f"错误：没有找到工具 {call['function']['name']}"
        else:
            result = tool_impl.run(**json.loads(call["function"]["arguments"]))
        self.session.messages.append({
            "role": "tool", "tool_call_id": call["id"], "content": result,
        })

几个关键设计：

  • 原生 function calling 协议：这里用的是 DeepSeek 原生的 tools 参数，模型返回结构化的 tool_calls，比"裸 JSON 约定"可靠得多。上一篇讲的裸 JSON 是理解原理的入口，原生协议是生产选择。
  • 工具结果作为 tool 消息回填：模型能"看到"调用结果，继续思考或修正。结果格式就是文本，天然兼容。
  • 错误也是上下文：工具不存在、参数错误时，把错误文本回填给模型，让它自我修正——而不是让整个 agent 崩溃。
  • max_steps 是硬边界：无论模型怎么绕，最多循环 N 步，防止死循环烧钱。

五、为什么这样设计

  • 显式注册，不藏全局状态：装饰器只负责"把函数包装成工具"，注册必须显式调用——和上一篇 Session 的哲学一致，状态的所有者要清楚。
  • 薄协议、厚循环：harness 不关心工具内部逻辑，只负责"表达意图 → 执行 → 回填"，工具本身由业务方提供。
  • 一个已知的坑：上下文裁剪时，tool 消息必须跟在对应的 tool_calls 后面，裁剪如果拆散配对会导致 API 报错。生产环境裁剪要对"调用-结果"成对处理，本系列从简，先记住这个坑。

六、小结

本篇的收获：

  1. Agent 的本质是一个"感知 → 思考 → 行动"循环，harness 负责把循环跑对、跑稳、跑得有限。
  2. 工具协议用原生 function calling（结构化 tool_calls），比裸 JSON 可靠。
  3. 错误回填给模型 = 给模型自我修正的机会；max_steps 是烧钱的刹车。
