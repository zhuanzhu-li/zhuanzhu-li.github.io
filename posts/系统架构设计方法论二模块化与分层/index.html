系统架构设计方法论（二）：模块化与分层

前言

需求与边界划清楚之后，下一个问题是怎么把系统组织成可维护的代码结构。最常见的失败不是没有架构，而是架构形同虚设：一个 5000 行的 Service 类、循环依赖成环、包结构按"controller/service/dao"机械分层，业务逻辑散落一地。

模块化与分层要解决的是复杂度的组织问题：让每个模块可以独立理解、独立修改、独立测试。

一、模块化：内聚与耦合

1.1 什么是好的模块

好的模块两个特征：高内聚（模块内部的东西强相关）和低耦合（模块之间弱依赖）。衡量手段：

  • 依赖方向：A 依赖 B、B 不依赖 A
  • 循环依赖：A→B→C→A，等于没有边界
  • 扇出/扇入：一个模块依赖太多（扇出大）或被人依赖太多（扇入大）都要警惕

1.2 循环依赖的识别与消除

循环依赖是模块化的头号杀手，识别方法很朴素：画依赖图，找环。

消除循环依赖三板斧：
1. 依赖倒置：把具体依赖改成接口依赖，环在接口层解开
2. 提取公共层：双方共享的部分下沉为公共模块
3. 事件化解耦：A 不直接调 B，通过事件/消息通信

代码层面用架构约束工具（如 ArchUnit、Maven Enforcer）把依赖规则固化成检查，违反即构建失败，比 code review 可靠得多。

二、分层架构与依赖倒置

2.1 经典分层

分层把系统按关注点切成横向层次，每层只依赖下层：

表现层（Controller / DTO）
   ↓
应用层（Service：用例编排）
   ↓
领域层（Entity / Domain Service：业务规则）
   ↓
基础设施层（Repository / MQ / 外部客户端）

分层的价值：每层只解决一类问题，替换和测试都容易。比如基础设施层的数据库从 MySQL 换成 PG，领域层代码不用动。

2.2 依赖倒置是关键

严格的分层不是"上层直接 new 下层"，而是依赖倒置：上层定义接口，下层实现接口，依赖方向反过来。

// 领域层只依赖接口
public interface OrderRepository {
    Order findById(Long id);
    void save(Order order);
}

// 基础设施层实现接口
@Repository
public class MyBatisOrderRepository implements OrderRepository {
    // 数据库访问细节全部在这里
}

这就是Spring 框架中的设计模式里讲的控制反转：容器负责组装，业务代码只面对抽象。

三、组织方式：按技术分层 vs 按业务聚合

包结构有两种组织哲学：

按技术分层（传统 MVC）           按业务聚合（package by feature）
com.app.controller                 com.app.order
com.app.service                      OrderController
com.app.dao                          OrderService
com.app.model                        OrderRepository
                                    com.app.payment
                                      PaymentController
                                      PaymentService
  • 按技术分层：结构简单，但需求变更要横跨多层改文件，内聚性差
  • 按业务聚合：一个业务功能的所有代码聚在一起，改需求只动一个包，边界清晰

现代实践更推荐按业务聚合为主，技术分层为内部纪律。支付系统就是典型：每个业务域一个包，包内再分 controller/service/repository。

四、防腐层与开放封闭

4.1 防腐层（ACL）

外部系统（第三方 API、遗留系统、异构系统）的模型和自己的领域模型不一致时，加一层防腐层做翻译，防止外部概念污染核心逻辑。

支付系统的渠道层就是标准的防腐层：微信、支付宝、银联的接口千差万别，但核心业务只面对统一的 ChannelAdapter 接口。这部分在支付系统架构设计（五）：支付网关与渠道路由里有详细展开。

4.2 开放封闭

模块对扩展开放、对修改封闭：新加一种渠道，通过实现新适配器完成，不改核心代码。这正是支付渠道层能持续加新渠道而核心不动的关键。

五、权衡取舍

  • 分层 vs 简洁：过度分层会让简单需求穿越五六层，徒增成本；原则是"层级服务于变化点"，没有变化点的层次可以砍掉
  • 抽象 vs 性能：每层抽象都有成本（对象转换、间接调用）；性能敏感路径可以绕过不必要的抽象，但要明确标注
  • 模块粒度：模块太小导致依赖爆炸，太大导致内聚失效；粒度跟着团队和变化走

六、落地案例：支付系统四层架构

支付系统架构设计（一）：整体架构概览给出了完整的四层架构：接入层、核心业务层、账务层、渠道层。这套分层的本质是关注点分离：

层 关注点 典型依赖
接入层 签名、限流、路由 Spring Cloud Gateway
核心业务层 支付编排、状态机 Spring Boot
账务层 记账、对账、清结算 分布式事务、定时任务
渠道层 外部渠道适配 HTTP 客户端、MQ

工程落地层面，Maven 多模块是模块化的标准载体：Maven 多模块项目与最佳实践讲了如何用 parent POM 统一依赖、用模块依赖约束边界——payment-common、payment-core、payment-channel 各司其职，编译期就防止了跨层依赖。

七、面试考察点与自查清单

高频面试题：

  1. “循环依赖怎么解决？"——依赖倒置、公共层提取、事件化解耦
  2. “MVC 分层和 DDD 分层有什么区别？"——DDD 多了领域层，业务规则落在领域层而非 Service
  3. “依赖倒置的意义？"——上层稳定、下层可替换、可测试
  4. “怎么防止架构腐化？"——依赖约束工具、架构评审、ADR

自查清单：

  • 能画出项目的依赖图，确认没有环
  • 能说出每个模块的边界和依赖方向
  • 领域层不依赖基础设施层的具体实现
  • 知道什么情况该用防腐层
