前言

调用大模型 API 已经不是新鲜事了。但"能调通"和"能工程化地调"之间，隔着一条很多人踩过的沟：key 写在哪、超时怎么办、限流怎么退避、失败怎么反馈给用户、代码怎么测试……这些细节散落在业务代码里，就是一笔笔技术债。

这个系列想做的事很明确：不依赖任何框架，从零手搭一个 AI Harness——把"模型"包起来的那层工程运行时。我们会像写业务代码一样，一篇文章加一个能力，每加一个能力就引出它背后真实的工程问题：上下文管理、工具调用、结构化输出、沙箱、可观测性、评测。

配套代码在仓库 ai-harness-tutorial，每篇文章对应一个 tag，你可以 clone 后 git checkout lesson-XX 直接看到那一篇的代码状态。本系列面向有后端基础、想真正搞懂 agent 每一层的工程师。

本篇是系列第一块砖：一次模型调用的最小封装。我们从"最朴素地调一次 DeepSeek"开始，看它怎么一步步长成一个 harness。

一、场景：给你的业务接上 DeepSeek

假设你的后端要加一个 AI 功能：用户提问，模型回答。听起来很简单——就是发一个 HTTP 请求：

POST https://api.deepseek.com/chat/completions
Content-Type: application/json
Authorization: Bearer <DEEPSEEK_API_KEY>

{
  "model": "deepseek-chat",
  "messages": [
    {"role": "user", "content": "用一句话介绍你自己"}
  ]
}

返回的 JSON 里，choices[0].message.content 就是模型的回答。第一版代码通常长这样。

二、朴素实现：能跑，但很脆

import os

import requests

API_KEY = os.environ["DEEPSEEK_API_KEY"]
URL = "https://api.deepseek.com/chat/completions"

resp = requests.post(
    URL,
    headers={"Authorization": f"Bearer {API_KEY}"},
    json={
        "model": "deepseek-chat",
        "messages": [{"role": "user", "content": "用一句话介绍你自己"}],
    },
)

print(resp.json()["choices"][0]["message"]["content"])

跑起来大概长这样：

$ python lessons/lesson_01/naive_call.py
我是 DeepSeek Chat，一个由深度求索公司开发的 AI 助手，专注于提供准确、实用的信息与帮助。

能跑。但别高兴太早——这段代码在真实项目里活不过第一周。

三、它暴露了哪些问题

  • 配置散落且硬编码：URL、模型名写死在代码里。换模型、换供应商、改超时，都要翻代码。
  • 没有超时：requests.post 默认无限等。模型偶发慢响应时，你的接口也跟着挂。
  • 没有错误处理：网络一抖抛 requests 异常；429 限流、5xx 直接崩；用户看到的是 500，没人知道为什么。
  • 成功路径也很脆：resp.json()["choices"][0]["message"]["content"] 任何一层结构不对就 KeyError。
  • 不可测试：想 mock 一次调用，得把 URL、headers、json 全部 mock 一遍，测试和实现强耦合。

这些问题的共同点是：模型调用的工程细节和业务代码混在一起。一个接口里混进了网络、错误处理、配置，业务逻辑反而看不清。

四、工程化演进：最小封装

harness 的第一步，就是把这些问题收进一个类里。原则很简单：调用方只关心"发消息、拿回复"，其余全部封装。

先看配置——从环境变量读取，缺 key 时给出看得懂的报错：

@dataclass
class LLMConfig:
    api_key: str
    base_url: str = "https://api.deepseek.com"
    model: str = "deepseek-chat"
    timeout: float = 30.0
    max_retries: int = 3

    @classmethod
    def from_env(cls):
        api_key = os.getenv("DEEPSEEK_API_KEY", "").strip()
        if not api_key:
            raise LLMConfigError("未设置 DEEPSEEK_API_KEY")
        return cls(api_key=api_key, ...)

再看核心的 LLMClient——超时、重试、错误分类都在这里收口：

class LLMClient:
    def __init__(self, config=None):
        self.config = config or LLMConfig.from_env()
        self.session = requests.Session()
        self.session.headers.update(
            {"Authorization": f"Bearer {self.config.api_key}"}
        )

    def chat(self, messages):
        # 带超时；429/5xx/网络异常指数退避重试；
        # 所有失败统一抛 LLMError，并标记 retryable
        ...

调用方变成了三行：

from dotenv import load_dotenv

from harness import LLMClient

load_dotenv()
client = LLMClient()
print(client.chat([{"role": "user", "content": "用一句话介绍你自己"}]))

这一版解决了朴素版的哪些问题：

朴素版问题 封装后的处理
配置硬编码 LLMConfig.from_env() 从环境变量读取，.env.example 留档
没有超时 统一 timeout=30s，可配置
没有错误处理 统一异常 LLMError，调用方能捕获并分类处理
失败就崩 429 / 5xx / 网络异常自动重试，指数退避
不可测试 可以注入 mock 配置和 session，测试只针对 chat() 的输入输出

完整代码见仓库 harness/llm.py（当前 tag lesson-01）。

五、为什么这样设计

  • 薄封装，不藏业务：LLMClient 只做"消息 → 文本"，不做业务判断。业务逻辑留在上层，harness 保持可复用。
  • 不用 SDK，用 requests：SDK 帮你省了 20 行，但把错误处理、重试、参数都变成黑盒。这个系列的目标是看懂每一层，所以先裸写。
  • 错误要可分类：retryable 标记让调用方知道"重试有用吗"——网络抖动重试有用，key 错了重试一万次也没用。
  • 为演进留接口：chat(messages) 这个签名，下一篇加多轮对话时不需要改调用方。

六、小结

本篇的收获：

  1. 模型调用不是"发个请求"，而是一堆工程细节：配置、超时、重试、错误分类。
  2. harness 的第一层，是把这些细节封装成可靠组件，让业务代码只关心输入输出。
  3. 设计上保持薄封装 + 错误可分类 + 可测试，为后面的演进打底。

配套仓库当前在 lesson-01 tag，代码见 harness/llm.py。
