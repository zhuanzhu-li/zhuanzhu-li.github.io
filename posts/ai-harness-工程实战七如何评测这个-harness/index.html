前言

前六篇，我们搭出了一个完整的 harness：模型封装、会话、上下文、工具循环、结构化输出、沙箱、可观测性。但还有一个终极问题没回答：改一行代码，怎么知道 agent 变好了还是变差了？

“感觉变聪明了"不算数。这一篇给 harness 装上最后一环：评测——fake LLM、eval 集、客观指标。这也是系列的收尾：七篇下来，一个从零手搭的 harness 完整闭环了。

一、场景：凭感觉改代码

你在第二篇把截断策略从"窗口"改成"摘要”，在第四篇把重试次数从 3 改成 5。怎么看效果？

  • 手动点几个例子？今天感觉好，明天感觉差，随机性让你永远分不清是改好了还是改坏了。
  • 直接上真实 API 跑？每轮评测都要花钱、要等、还会因为模型随机性抖动。

评测要解决的就是这三个问题：客观、可复现、低成本。

二、朴素实现：手动点几个例子

print(agent.run("北京天气怎么样？"))   # 看一眼，感觉还行
print(agent.run("1+2 等于几？"))       # 嗯，这个也差不多

两个用例、一双肉眼、一个"感觉"。这不是评测，这是许愿。

三、它暴露了哪些问题

  • 没有客观指标：通过/失败全靠人判断，同一个回答今天算过、明天算不过。
  • 样例覆盖不足：两三个手工用例发现不了回归——上下文截断坏了、工具权限放宽了，都测不出来。
  • 随机性干扰：真实模型输出不稳定，两次跑同一套用例结果不一样，无法定位是代码问题还是模型抖动。
  • 成本不可控：每次评测都调真实 API，改动频繁时账单先崩溃。

四、工程化演进：FakeLLM + eval 集 + 指标

1. FakeLLM：把模型换成脚本

核心思路：评测 harness 逻辑时，不依赖真实模型。FakeLLM 按脚本顺序返回预设响应：

llm = FakeLLM([
    {"role": "assistant", "content": None, "tool_calls": [...]},  # 第一轮：调工具
    {"role": "assistant", "content": "结果是 3"},                  # 第二轮：回答
])

没有随机性、不花钱、毫秒级跑完。它能测的是 harness 的逻辑：循环是否收敛、工具是否执行、权限是否拦截、上下文是否裁剪、成本是否统计。真实模型的质量评测，再把 FakeLLM 换成 LLMClient() 就行——框架不变。

2. eval 集与指标

EvalCase 定义一个测试任务（输入 + 期望），run_eval 批量跑并产出指标：

cases = [
    EvalCase("北京天气", "北京天气怎么样？", ["28"]),
    EvalCase("上海天气", "上海天气呢？", ["多云"]),
]
report = run_eval(build_agent, cases)

成功率：1.0（3/3）
平均步数：2.0，总成本：$0.0
  [PASS] 北京天气 -> 北京天气：晴，28°C

三个指标分别回答三个问题：成功率（功能对不对）、平均步数（效率高不高，绕圈子会体现）、总成本（贵不贵，接上第六篇的 Telemetry 自动累计）。

3. 单元测试：把前六篇的能力全部钉住

评测面向 agent 行为，单元测试面向 harness 组件。仓库的 tests/ 里现在有 21 个测试，覆盖前六篇的每个模块：

测试文件 覆盖
test_context.py token 估算、窗口截断、摘要压缩
test_output.py JSON 解析、Schema 校验、内容重试
test_retry.py 指数退避、重试耗尽
test_sandbox.py 路径穿越、命令白名单、越界读
test_eval.py FakeLLM、eval 指标、异常兜底

跑一次：python -m unittest discover -s tests。以后改任何一行，先跑测试——回归在提交前被发现，而不是上线后。

4. 真实评测的注意点

换真实模型评测时：

  • temperature 设 0：减少随机性，让差异主要来自代码改动（LLMClient 默认就是 0）。
  • 固定 eval 集：同一套用例、同一批参数，对比才有意义。
  • 控制成本：先用 FakeLLM 跑逻辑测试，再小范围跑真实评测；成功率、步数、成本三个指标一起看。

五、为什么这样设计

  • 逻辑评测和模型评测分离：harness 的代码逻辑用 FakeLLM 测（快、稳、免费），模型本身的水平用真实 eval 测（慢、贵、有方差）——两者不混，才能定位问题。
  • 指标要能对比：成功率、步数、成本都是数值，改代码前后各跑一次，数字说话。
  • 评测和测试互补：单元测试保证组件不回归，eval 保证整体行为不退化，缺一不可。

每一层都回答了一个真实的工程问题：为什么需要封装（1）、状态怎么管理（2）、循环怎么跑（3）、输出怎么可信（4）、边界怎么守（5）、黑盒怎么打开（6）、改动怎么验证（7）。
