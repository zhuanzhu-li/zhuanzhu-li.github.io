前言

前三篇，harness 会聊天、会记上下文、会调工具了。但有一个问题一直悬着：模型输出的是文本，业务要的是数据。不管是"从会议记录里提取字段"还是"把工具调用参数标准化"，只要模型输出 JSON，就绕不开两件事：解析、校验。而一旦有"可能失败"的操作，就绕不开第三件事：重试。

这一篇把这三件事做扎实。

一、场景：业务要的是可靠 JSON

假设你的产品要自动从会议记录里提取结构化信息：

{
  "date": "2026-08-07",
  "attendees": ["张三", "李四"],
  "action_items": ["下周五前完成原型"]
}

下游接口、数据库、任务系统都要这个结构。模型输出只要差一点——多一句解释、少一个字段、日期变成字符串还是数字没说清——下游就崩。

二、朴素实现：json.loads 赌一把

reply = client.chat([{"role": "user", "content": prompt}])
data = json.loads(reply)          # 祈祷
return data["date"]               # 祈祷字段在

本地调通三次，就以为稳了。上线第一周，JSONDecodeError 和 KeyError 轮流值班。

三、它暴露了哪些问题

  • 模型输出天生不守规矩：可能给你 markdown 围栏（```json）、前后夹带"好的，结果如下"、甚至输出被截断成半个 JSON。
  • 只解析不校验：JSON 合法 ≠ 业务可用。字段缺了、类型错了、日期格式不对，json.loads 全都不知道。
  • 失败后没策略：解析失败就报错，不重试；真要重试，也是"死循环重试"——没有退避、没有上限、不知道什么错值得重试。
  • 把两类重试混为一谈：网络超时重试和"内容不合格重试"是两件事，前者等一等就好，后者要把错误反馈给模型让它改。

四、工程化演进：解析 → 校验 → 内容重试

1. 容错解析：先把 JSON 捞出来

parse_json 按"由严到松"的三级策略来：

def parse_json(text: str):
    stripped = text.strip()
    try:
        return json.loads(stripped)              # 1. 整体解析
    except json.JSONDecodeError:
        pass
    fenced = re.search(r"```(?:json)?\s*(.*?)```", stripped, re.DOTALL)
    if fenced:
        try:
            return json.loads(fenced.group(1))   # 2. 剥 markdown 围栏
        except json.JSONDecodeError:
            pass
    # 3. 从第一个 { 或 [ 截到最后一个 } 或 ]，容忍前后夹带文字
    ...

三种情况：干净输出直接解析；带围栏剥掉再解析；夹带废话截取 JSON 部分。全失败才抛错——先给模型最大宽容，最后一道防线才报错。

2. Schema 校验：JSON 合法 ≠ 业务可用

解析出 dict 只是第一步，还得校验字段和类型：

schema = OutputSchema(
    fields={"date": as_str, "attendees": as_list, "action_items": as_list},
    required=["date", "attendees", "action_items"],
)
result = schema.validate(data)   # 缺字段、类型错都会抛带说明的 ValueError

校验函数就是一个"类型守卫"：as_str、as_int、as_list，不合格抛异常，异常信息就是给模型的"整改意见"。

3. 内容重试：把错误反馈给模型

解析或校验失败后，最有效的不是"再问一遍"，而是把失败原因告诉模型，让它改：

convo.append({"role": "assistant", "content": content})          # 它刚才的输出
convo.append({"role": "user",
              "content": f"输出不符合要求：{exc}。请只输出符合格式的 JSON。"})
data = client.chat_completion(convo)

chat_json 把"调用 → 解析 → 校验 → 反馈 → 重试"收进一个函数，最多 N 次：

result = chat_json(
    LLMClient(), messages, schema,
    retry_policy=RetryPolicy(max_attempts=3, base_delay=0.2),
)

4. 统一重试策略：指数退避 + 抖动

重试不能蛮干。RetryPolicy 提供指数退避和抖动（jitter）：

@dataclass
class RetryPolicy:
    max_attempts: int = 3
    base_delay: float = 1.0
    max_delay: float = 8.0
    jitter: bool = True

    def delay(self, attempt: int) -> float:
        wait = min(self.max_delay, self.base_delay * (2 ** (attempt - 1)))
        if self.jitter:
            wait = wait * random.uniform(0.5, 1.0)
        return wait

为什么要有 jitter？如果没有，100 个请求同时失败、同时退避、同时重试，会把下游再打崩一次——重试风暴。加一点随机抖动，把重试时间错开。

顺便，上一版的网络重试也重构进了 retry()，LLMClient 现在的重试逻辑统一走 RetryPolicy，网络错误按 retryable 标记决定要不要重试。

五、为什么这样设计

  • 解析宽容、校验严格：解析负责"把模型输出变成 JSON"，尽量包容；校验负责"把 JSON 变成业务数据"，一点不让。两层职责分开，各改各的。
  • 内容重试 vs 网络重试分开：网络重试是"等一等再来"，内容重试是"告诉模型哪里错了再来"——两者都复用退避策略，但语义完全不同，不能混。
  • 重试必须有预算：max_attempts 是上限，配上指数退避，最坏情况也花得起；“无限重试"不是可靠性，是事故。
  • 错误信息可读：校验异常直接拼接进反馈 prompt，模型的修正更有针对性。

六、小结

本篇的收获：

  1. 结构化输出 = 容错解析 + 严格校验，两步各司其职。
  2. 内容重试的正确姿势是"反馈错误给模型”，而不是盲目重问。
  3. 重试要讲策略：指数退避 + jitter + 上限，网络重试和内容重试分开管理。
