前言

第五篇之前，harness 会聊天、会调工具、会守边界。但它仍然是个黑盒：一次任务跑了 5 轮循环、调了 3 次工具、花了多少钱、哪一步出的问题——没人知道。

这一篇做三件事：结构化日志（每步干了什么）、事件钩子（谁都能订阅）、成本核算（每次调用花了多少 token 和钱）。做完之后，agent 不再是黑盒，出问题能按图索骥。

一、场景：agent 跑挂了，没人知道哪一步

线上一个 agent 任务失败。你问自己：

  1. 它调了几次模型？每次多少 token？
  2. 它调了哪些工具？参数是什么？哪个工具返回了异常？
  3. 哪一步开始偏离预期？

如果代码里只有 print("调用了工具")，这三个问题一个都答不上来。

二、朴素实现：print 大法

print("开始执行")
print("调用工具：", tool_name)
print("结果：", result)
print("完成")

本地调试够用，上线之后：日志被刷屏、检索靠眼、多用户请求互相串、想按"某一次任务"查日志根本做不到。

三、它暴露了哪些问题

  • 日志没有结构：print 输出是给人看的，不是给系统检索的。想按 request_id、事件类型过滤？没有。
  • 关键动作没埋点：token、成本、模型名、上下文大小这些"运维数据"根本没记录。
  • 流程无法串联：一次任务有多次模型调用 + 多次工具调用，彼此之间没有关联标识，出了问题拼不出因果链。
  • 埋点侵入业务：硬编码的 print 散落在各处，想接日志系统要改一堆代码。

四、工程化演进：事件总线 + 结构化日志 + 成本核算

1. 事件总线：每个关键动作发一个事件

Telemetry 是一个极简事件总线，emit 把事件写成结构化 JSON 日志，同时通知订阅者：

@dataclass
class Telemetry:
    def emit(self, event: str, data: dict) -> None:
        payload = {
            "event": event,
            "request_id": self.request_id,   # 贯穿一次任务
            "ts": time.time(),
            **data,
        }
        logger.info(json.dumps(payload, ensure_ascii=False))
        if self.on_event is not None:
            self.on_event(event, payload)     # 订阅者：打印、接监控系统都行

request_id 在 Telemetry 创建时生成，贯穿整个任务——这就是"链路追踪"的最小形态：一次任务的所有日志，用同一个 id 串起来。

2. 接入模型调用：usage 与成本

模型响应自带 usage（prompt/completion/total tokens）。LLMClient 在每次成功后把它记入 Telemetry，并按价格表折算成本：

telemetry.record_usage(Usage(prompt_tokens, completion_tokens, total_tokens))
telemetry.emit("llm.call", {
    "model": self.config.model,
    "total_tokens": total_tokens,
    "cost_usd": round(cost_usd, 6),
})

一个关键工程细节：埋点失败不能影响主流程。_record_usage 整体包在 try/except 里，Telemetry 挂了，模型调用照常返回——可观测性永远不能成为可用性的依赖。

3. 接入 Agent：步骤、工具调用 span

Agent 在循环的每个关键节点发事件：

telemetry.emit("agent.start", {"input": user_input, "max_steps": self.max_steps})
telemetry.emit("agent.step", {"step": step, "context_tokens": ...})

span_id = telemetry.start_span("tool.call", {"tool": tool_name, "arguments": arguments})
result = tool_impl.run(**arguments)
telemetry.end_span(span_id, {"tool": tool_name, "result_len": len(result)})

telemetry.emit("agent.end", {"steps": step, "answer_len": len(content)})

start_span / end_span 是简化版 tracing：记录一次工具调用的耗时（duration_ms）。生产环境可以换成 OpenTelemetry，但思路一模一样。

4. 汇总

一次任务结束，summary() 给出账单式汇总：

{'calls': 3, 'prompt_tokens': 4120, 'completion_tokens': 356,
 'total_tokens': 4476, 'cost_usd': 0.00114}

五、为什么这样设计

  • 结构化优先：JSON 日志可以被日志系统直接索引；print 不能。
  • 事件总线解耦：harness 不知道订阅者是谁，只负责发事件——接日志、接监控、接 UI 都是订阅者的事，harness 代码不用改。
  • 数据进、成本出：usage 是模型 API 自带的数据，harness 只负责收集和折算；成本透明，才能做预算控制（下一篇评测里会用到）。
  • 埋点零风险：可观测性代码永远不能让主流程更脆弱。

六、小结

本篇的收获：

  1. 可观测性 = 结构化日志 + 事件钩子 + 成本核算，三者合起来让 agent 不再是黑盒。
  2. request_id 贯穿 + span 记录耗时，就是最小可用的链路追踪。
  3. 埋点必须零侵入主流程，失败也不影响调用。
